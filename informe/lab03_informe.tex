\section*{1. Descripción de actividades}
\addcontentsline{toc}{section}{1. Descripción de actividades}
El objetivo de este laboratorio fue auditar la transformación de contraseñas en páginas web desde el lado del cliente y evaluar la reutilización de un hash para iniciar sesión, mediante una prueba de Pass the Hash.\par
Se seleccionó \url{https://www.forodvd.com/} y se creó una cuenta de prueba perteneciente al estudiante, con una contraseña destinada a esta actividad. Se trabajó con Ubuntu en VMware Workstation y con el navegador integrado de Burp Suite Community.\par
Se realizaron las siguientes actividades:\par
$\bullet$ Se identificó el algoritmo hash utilizado al registrar la cuenta.\par
$\bullet$ Se compararon los parámetros enviados durante el inicio de sesión.\par
$\bullet$ Se calculó el hash de la contraseña desde la consola del navegador.\par
$\bullet$ Se detuvo una solicitud de login en Proxy Intercept de Burp Suite.\par
$\bullet$ Se comprobó el rechazo de una contraseña incorrecta y se repitió el acceso sustituyendo sus hashes por el valor correcto.\par
$\bullet$ Se revisaron la política de privacidad enlazada por el sitio y los controles observados en la interfaz.\par
$\bullet$ Se elaboraron cuatro conclusiones sobre los resultados y su alcance.\par
La práctica mostró que el registro y el login enviaron MD5 en el cliente. La contraseña incorrecta fue rechazada, mientras que la solicitud con el hash correcto reutilizado abrió una sesión. La cuenta mantuvo pendiente la activación por correo para participar en el foro.\par
Al concluir, se envió un cambio de contraseña y se conservó la confirmación de actualización del perfil. La contraseña nueva no forma parte de las evidencias.\par

\subsection*{2.1. Hash en el registro}
\addcontentsline{toc}{subsection}{2.1. Hash en el registro}
Después de registrar la cuenta, se identificó en Burp la solicitud POST a \nolinkurl{/register.php?do=addmember}. Los parámetros \nolinkurl{password_md5} y \nolinkurl{passwordconfirm_md5} contenían el mismo valor. Los campos password y passwordconfirm aparecían vacíos.\par
\begin{lstlisting}
password_md5 = 95e5ffce381c006ca63266ecc0ac6771
passwordconfirm_md5 = 95e5ffce381c006ca63266ecc0ac6771
\end{lstlisting}
Se identificó MD5 mediante la biblioteca pública \href{https://www.forodvd.com/clientscript/vbulletin_md5.js?v=423}{\nolinkurl{vbulletin_md5.js}} y la coincidencia con \nolinkurl{hex_md5} al ingresar la misma contraseña en la consola. El tamaño de 32 caracteres hexadecimales es compatible con MD5, pero la identificación también se apoyó en el código y en esa comparación.\par

\subsection*{2.6. Privacidad y seguridad}
\addcontentsline{toc}{subsection}{2.6. Privacidad y seguridad}
El enlace Privacidad del pie de ForoDVD dirige a la política de protección de datos de HD Bits. Ese documento se revisó como política publicada por el operador del sitio.\par
\subsection*{Contenido de la política publicada}
La política identifica a HD Bits Networks SL como responsable del tratamiento. Declara confidencialidad de los datos y reconoce derechos de acceso, rectificación, cancelación y oposición. Indica que una cesión de datos a terceros requeriría informar al usuario y solicitar su consentimiento. También describe comunicaciones comerciales voluntarias y la gestión de preferencias desde el perfil del foro.\par
La política declara: «Sus datos serán tratados con absoluta confidencialidad».\par
El texto revisado no detalla el algoritmo usado para las contraseñas, sal, iteraciones, almacenamiento, longitud mínima ni autenticación de varios factores. Por ello, la política aporta compromisos generales sobre datos personales, pero no permite determinar cómo se protegen las contraseñas en el servidor.\par
Enlace a la política:\\
\url{https://www.hdbits.es/politica-de-proteccion-de-datos/}\par

\subsection*{2.7. Conclusiones sobre la seguridad}
\addcontentsline{toc}{subsection}{2.7. Conclusiones sobre la seguridad}
\subsection*{1. El cliente envía un hash que se mantiene estable}
Para la contraseña de prueba, el registro, la consola y los dos campos del login produjeron el mismo MD5. El cálculo observado no incorporó un reto variable al valor enviado. Esto permitió identificar una credencial derivada estable en las operaciones analizadas.\par
\subsection*{2. El hash capturado permitió autenticar el acceso}
El acceso con contraseña incorrecta fue rechazado. Al repetir el intento y reemplazar ambos hashes por el valor correcto, el sitio abrió una sesión. Por tanto, quien dispusiera de ese valor y de una solicitud válida podría intentar usarlo como credencial en el contexto probado. El experimento permitió comprobar la reutilización del hash como credencial en el flujo analizado.\par
\subsection*{3. Los controles adicionales tienen funciones diferentes}
El sitio validó el valor recibido y anunció límites para intentos fallidos. También mantuvo la activación por correo pendiente para participar. En la prueba, estos controles coexistieron con la aceptación del hash correcto reutilizado. El límite de intentos no se evaluó hasta el bloqueo y la activación no se eludió.\par
\subsection*{4. El análisis del cliente tiene un alcance concreto}
Observar MD5 en el navegador y reutilizar ese valor no permite conocer cómo el servidor guarda las contraseñas. La política revisada tampoco publica esos detalles. La conclusión comprobada se limita a la aceptación del hash como credencial en esta cuenta y este flujo. Una evaluación del almacenamiento o de otras cuentas requeriría evidencia adicional.\par
\section*{Conclusiones y comentarios}
El hash enviado por el cliente debe protegerse como una credencial cuando su posesión permite iniciar sesión. La práctica comprobó este comportamiento mediante el rechazo del control incorrecto, la sustitución de ambos hashes y el acceso posterior con la cuenta propia.\par
En Configuración se abrió Editar correo y contraseña, se completaron los campos de contraseña actual, nueva y confirmación, y se seleccionó Guardar cambios. El sitio confirmó la actualización del perfil. No se volvió a probar el hash antiguo después del cambio.\par
